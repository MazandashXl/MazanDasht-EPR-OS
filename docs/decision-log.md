# دفتر تصمیم‌ها (Decision Log)

این فایل مرجع تصمیم‌های پروژه است (سطح ۲ در سلسله‌مراتب تصمیم).

## قواعد این فایل

1. هر تصمیم یک شناسه `DL-NNNN` دارد و **هرگز حذف نمی‌شود**؛ فقط `Superseded` می‌شود.
2. **فقط مالک محصول** می‌تواند وضعیت را `Accepted` کند. عامل کدنویس حداکثر `Proposed` می‌سازد.
3. تصمیم `Accepted` بر اسناد و کد اولویت دارد؛ تصمیم `Proposed` هیچ اولویتی بر رفتار فعلی ندارد.
4. هر تعارض بین Prompt مادر، `PROJECT_SPEC.md`، اسناد `docs/` و کد، باید اینجا ثبت شود — حتی اگر حل نشود.
5. تصمیم‌های مالی (واحد پول، صول، صافی، ارزش‌گذاری، posting) بدون `Accepted` مالک محصول **و** حسابرس، مبنای کد نمی‌شوند.

### وضعیت‌ها

| وضعیت | معنی |
|---|---|
| `Proposed` | پیشنهاد عامل یا مالک؛ بدون اعتبار اجرایی |
| `Accepted` | تأییدشده توسط مالک محصول؛ مبنای کد |
| `Rejected` | رد شده؛ نباید پیاده شود |
| `Superseded` | جایگزین شده با تصمیم جدیدتر (با ارجاع) |
| `Blocked` | نیازمند ورودی بیرونی |

## DL-0001 — ورودی‌های الزامی Prompt 00 در مخزن موجود نیستند

- **وضعیت:** `Blocked`
- **تاریخ:** ۱۴۰۴/۰۸/۰۲
- **ثبت‌کننده:** عامل کدنویس
- **مرتبط:** `AUDIT-00`، `REQ-AUD-002`

### زمینه
دستور مادر می‌گوید «ابتدا فقط `prompts/00-*` را اجرا کن» و MVP دسکتاپ Python/Tkinter+SQLite در `desktop/` قرار دارد.
شاهد مشاهده‌شده:

| مورد | نتیجه |
|---|---|
| `prompts/` | وجود ندارد |
| `PROMPT_INDEX_00_TO_35_FA.md` | وجود ندارد |
| `PROJECT_SPEC.md` | وجود ندارد |
| `desktop/` | وجود ندارد |
| `docs/financial/*` (۴ سند) | وجود ندارند |
| `docs/03-...`، `docs/13-...` | وجود ندارند |
| کد محصول (`.py` محصول) | صفر فایل |
| Pull Request | صفر |
| تاریخ ایجاد repo | امروز، ۲ commit |

### تصمیم ثبت‌شده (واقعیت، نه انتخاب)
تا زمان تحویل بسته ورودی، هیچ توسعه‌ای انجام نمی‌شود. تخمین spec و ساختن MVP از صفر، با دستور «با حدس پیش نرو» و «ارزش‌گذاری/posting بدون مصوبه ممنوع» ناسازگار است.

### برای رفع
مالک محصول یکی از موارد بخش «گزینه‌های رفع انسداد» در `AUDIT-00` بند ۱۱ را انتخاب کند.

<a id="dl-0002"></a>
## DL-0002 — نمایش پول در ledger: integer rial در برابر `numeric(20,4)`

- **وضعیت:** `Proposed`
- **تاریخ:** ۱۴۰۴/۰۸/۰۲
- **مرتبط:** `REQ-MONEY-001`، `docs/financial/MONEY_UNIT_POLICY_FA.md` (غایب)، `database/schema.sql`

### زمینه
سیاست غیرقابل‌تغییر Prompt مادر: «مبالغ ledger به integer rial؛ ۱ تومان = ۱۰ ریال؛ محاسبات مالی با float ممنوع».
واقعیت مخزن: `database/schema.sql` ستون‌های مالی را `numeric(20,4)` تعریف کرده است (`fin_voucher_line.debit/credit`، `sal_invoice.*`، `inv_lot.cost_per_kg` و …) و ویوها/seed بر همین مبنا نوشته شده‌اند.

نکته: `numeric` در PostgreSQL نوع اعشاری دقیق است، پس **نقض «float ممنوع» نیست**؛ اما با «integer rial» ناسازگار است و ریسک دوگانگی واحد در محاسبات آینده دارد.

### گزینه‌ها

| # | گزینه | مزیت | ریسک |
|---|---|---|---|
| A | `bigint` برای همه مبالغ ریالی ledger؛ اعشار فقط در لایه محاسبه/نمایش | منطبق با سیاست؛ خطای گرد کردن حذف می‌شود | نیازمند بازنویسی DDL/ویوها؛ محاسبات درصدی نیاز به rounding صریح |
| B | حفظ `numeric(20,4)` + CHECK که مقدار همیشه صحیح باشد | کمترین تغییر | شکنندگی؛ سیاست «integer» دقیقاً اجرا نمی‌شود |
| C | `numeric` با مقیاس ۰ (`numeric(20,0)`) | نوع عددی دقیق و صحیح | تفاوت تایپ با `bigint`؛ سازگاری ابزار |

### پیشنهاد عامل
گزینه **A** برای جداول ledger و invoice؛ مبالغ مشتق (نرخ، درصد، cost_per_kg) می‌توانند اعشاری بمانند اما در مرز ثبت به ریال صحیح گرد شوند. اجرا **پس از** قرائت `MONEY_UNIT_POLICY_FA.md` و تأیید حسابرس.

> تا `Accepted` شدن، هیچ کد مالی جدید بر مبنای این اسناد ساخته نمی‌شود.

## DL-0003 — فناوری هدف: Python/Tkinter + SQLite در برابر .NET 8 + Vue/Electron + PostgreSQL

- **وضعیت:** `Proposed`
- **تاریخ:** ۱۴۰۴/۰۸/۰۲
- **مرتبط:** `REQ-AUD-005`، `docs/architecture/technical-architecture.md`، `docs/adr/0001..0006`

### زمینه
Prompt مادر: «فناوری فعلی MVP Python/Tkinter + SQLite است» و «اگر Windows 7 قطعی است، runtime/GUI/packaging باید روی سیستم هدف آزمون شود».
مخزن: `docs/architecture/technical-architecture.md` و ADR-0001..0006 معماری .NET 8 + PostgreSQL + Vue/Electron را `Accepted` اعلام کرده‌اند (یا در سند پیشنهاد شده‌اند) — بدون هیچ کد.

### گزینه‌ها

| # | گزینه | مزیت | ریسک |
|---|---|---|---|
| A | Python/Tkinter + SQLite به‌عنوان تنها مسیر واقعی؛ اسناد .NET به «طرح آینده» تنزل | منطبق با Prompt؛ سرعت تحویل؛ Win7 با Python 3.8 | محدودیت UI/گزارش‌سازی؛ نگهداشت بلندمدت |
| B | حفظ دو مسیر: MVP پایتون برای عملیات، سرویس .NET برای مالی | تفکیک مسئولیت | دو سیستم، دو مدل داده، پیچیدگی همگام‌سازی |
| C | رفتن به .NET/Vue از ابتدا | معماری قوی‌تر | بازنویسی، Win7 محدود، زمان زیاد |

### پیشنهاد عامل
گزینه **A** برای نسخه ۱ (مبتنی بر Prompt)؛ اسناد `.NET/PostgreSQL` با برچسب «Target Architecture (Not Implemented)» نگه داشته شوند تا گمراه‌کننده نباشند. اجرا پس از `Accepted` شدن.

<a id="dl-0004"></a>
## DL-0004 — اسناد معماری موجود تأیید مالک محصول ندارند

- **وضعیت:** `Proposed`
- **تاریخ:** ۱۴۰۴/۰۸/۰۲
- **مرتبط:** کل `docs/`، `docs/00-foundations/team-governance.md`

### زمینه
مجموعه ۵۸ سندی موجود (۶ جلد) در نوبت قبل توسط عامل تولید شده است. در سلسله‌مراتب تصمیم، این اسناد «قرارداد دامنه» محسوب می‌شوند **تنها اگر** تأیید شده باشند. هیچ شاهد تأیید مالک محصول یا حسابرس وجود ندارد (بخش «پذیرش» اسناد، چک‌لیست برای آینده است، نه امضا).

### تصمیم ثبت‌شده
- اسناد `docs/` تا اعلام نظر مالک محصول، `Proposed` تلقی می‌شوند.
- **جایگزین** اسناد مالی الزامی Prompt مادر نیستند (خصوصاً `docs/financial/*` که موجود نیستند).
- آن‌چه در آن اسناد «قطعی» نوشته شده (مثل ۱۲ اصل غیرقابل مذاکره، ۳۲ سناریوی سند خودکار، سیاست صفر بودن ارزش ضایعات در ADR-0007) **بدون مصوبه، مبنا نیست**.

### برای رفع
مالک محصول فهرست اسناد مورد تأیید را (به‌صورت گروهی یا موردی) در همین فایل ثبت کند؛ در آن صورت وضعیت `Accepted` می‌گیرند.

<a id="dl-0005"></a>
## DL-0005 — محدودیت اثبات در محیط سندباکس

- **وضعیت:** `Proposed` (ثبت محدودیت)
- **تاریخ:** ۱۴۰۴/۰۸/۰۲
- **مرتبط:** تعریف `VERIFIED ON TARGET`

### زمینه
محیط اجرای عامل: Debian 12، Python 3.11.2، SQLite 3.40.1، **بدون `tkinter`**، بدون `DISPLAY`، بدون PyInstaller، بدون دسترسی به ویندوز.

### پیامد
| سطح | امکان در این محیط |
|---|---|
| منطق دامنه/DB (headless) | ✅ قابل اجرا و آزمون |
| GUI (Tkinter) | ❌ اجرا ممکن نیست |
| بسته نصبی Windows | ❌ ساخت و آزمون ممکن نیست |
| Windows 7 SP1 x64 | ❌ ممکن نیست |

### تصمیم ثبت‌شده
- هیچ ادعای `VERIFIED ON TARGET` بدون شاهد از سیستم هدف مالک محصول ثبت نمی‌شود.
- برای GUI، حداکثر `IMPLEMENTED` + شاهد آزمون دستی مالک محصول یا `TESTED` با تست headless منطق جدا‌شده.
