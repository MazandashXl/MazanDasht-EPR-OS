# ADR-0006 — تقویم شمسی و ذخیره‌سازی UTC

- تاریخ: ۱۴۰۴/۰۸/۰۲ · وضعیت: **Accepted**
- تصمیم‌گیرندگان: معمار ERP، حسابرس ارشد، مهندس UX
- مرتبط: REQ-F-012

## زمینه
کاربران با تاریخ شمسی کار می‌کنند؛ اما ذخیره رشته شمسی، مرتب‌سازی، بازه‌گیری و مقایسه را خراب می‌کند.

## گزینه‌ها
1. ذخیره رشته شمسی (`varchar`) — ساده در نمایش، فاجعه در گزارش.
2. ذخیره `date` میلادی + تبدیل در لبه — استاندارد.
3. ذخیره عدد سریال شمسی — غیرقابل خواندن و وابسته به کتابخانه.

## تصمیم
گزینه ۲:
- `business_date date` میلادی برای همه تاریخ‌های کاری.
- `timestamptz` UTC برای رخدادها.
- تبدیل شمسی فقط در Backend (نمایش) و Frontend (ورودی/نمایش).
- تست مرزی: ۲۹/۳۰ اسفند، سال کبیسه، ورودی‌های متنی، سریال اکسل.
- `bi_dim_date` شامل هر دو تقویم برای گزارش.

## پیامدها
- مثبت: گزارش و بازه‌گیری دقیق؛ سازگاری با ابزارهای استاندارد.
- منفی: هر نمایش باید تبدیل شود (ریسک فراموشی) → تابع مشترک اجباری و تست واژه‌نامه.
