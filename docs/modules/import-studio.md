# Import Studio — واردسازی هوشمند اسناد

سند مرجع: `MD-MOD-IMP-001` · نسخه ۱.۰ · مالک: معمار ERP · بازبین: حسابرس مالی، UX

> امروز یک ماه صورتحساب بانکی، ۲ تا ۴ ساعت کار دستی است و ۲ تا ۵ درصد خطا دارد. هدف: **۱۰ دقیقه، صفر خطای تکرار، و یک سند قابل حسابرسی برای هر ردیف.**

---

## ۱. دامنه

| نوع ورودی | منبع | خروجی |
|---|---|---|
| صورتحساب بانکی | xlsx / csv / pdf متنی | اسناد دریافت/پرداخت + تطبیق |
| فهرست مشتریان/باغداران | xlsx / csv | طرف حساب جدید (با تأیید) |
| فهرست کالا و قیمت | xlsx / csv | کالا/قیمت |
| موجودی اول دوره | xlsx | سند افتتاحیه موجودی |
| فاکتورهای قدیمی (مهاجرت) | xlsx | فاکتور + سند |
| اسناد حسابداری دستی | xlsx | سند دوبل |
| تراکنش دستگاه باسکول قدیمی | csv | قبض باسکول (مهاجرت) |

**اصول چهارگانه:**

1. **هیچ ثبت بدون پیش‌نمایش.** (VIS-07)
2. **هیچ ردیف بدون ردیابی به فایل و سطر.** (`source_ref`)
3. **هیچ تکراری، دوبار ثبت نمی‌شود.**
4. **هر دسته، یک دکمه برگشت دارد.**

---

## ۲. جریان پنج مرحله‌ای

```
1. UPLOAD      آپلود → تشخیص نوع و بانک از «اثر انگشت فایل»
2. MAP         نگاشت ستون‌ها (گرافیکی، Drag & Drop) + ذخیره Template
3. PREVIEW     پیش‌نمایش کامل با وضعیت هر ردیف: جدید / تکراری / مشکوک / ناقص
4. REVIEW      بازبینی انسانی ردیف‌های مشکوک + تأیید
5. POST        ثبت اتمیک دسته + گزارش + امکان Rollback
```

## ۳. مرحله ۱ — پذیرش و تشخیص

### ۳.۱ اثر انگشت فایل (File Fingerprint)

```
fingerprint = hash(
   header_signature        // مجموعه نرمال‌شده نام ستون‌ها، مرتب‌شده
   + column_count
   + first_data_row_shape  // نوع داده هر ستون در اولین سطر داده
   + delimiter/encoding
)
```

| نتیجه تطبیق | رفتار |
|---|---|
| اثر انگشت دقیقاً منطبق با Template | اعمال خودکار، پرش به مرحله ۳ |
| منطبق با ≥ ۸۰٪ شباهت | پیشنهاد Template با نمایش تفاوت |
| هیچ انطباق | نگاشت دستی از صفر |

### ۳.۲ پشتیبانی قالب‌های بانکی

| بانک | ویژگی فایل | نکات |
|---|---|---|
| ملت | ستون‌های «تاریخ / شرح / بدهکار / بستانکار / مانده» | تاریخ شمسی، گاهی دو سطر سرستون |
| ملی | «تاریخ / کد تراکنش / بابت / واریز / برداشت» | شرح چندخطی |
| تجارت | «تاریخ عمل / شماره سند / شرح / مبلغ / نوع» | مبلغ با علامت |
| صادرات | «تاریخ / شماره پیگیری / بابت / مبلغ بدهکار / بستانکار» | برخی نسخه‌ها با ستون مانده |
| سپه | «تاریخ / ساعت / شرح / برداشت / واریز» | ستون ساعت |
| پاسارگاد | «تاریخ / زمان / شرح / مبلغ / مانده» | مبلغ با علامت مثبت/منفی |

**قالب جدید** را کاربر یک بار می‌سازد؛ از آن پس، برای همان حساب بانکی خودکار اعمال می‌شود (BR-524).

### ۳.۳ پیش‌پردازش خودکار فایل

| مشکل رایج | درمان خودکار |
|---|---|
| سطر عنوان و لوگو در بالای جدول | تشخیص سطر سرستون با «چگالی متن و یکتایی» |
| سلول‌های ادغام‌شده | پرکردن رو به پایین |
| اعداد با ارقام فارسی/عربی | تبدیل به لاتین |
| جداکننده هزارگان و «٬» | حذف |
| منفی به‌صورت `(۱۲۳)` یا `۱۲۳-` | نرمال‌سازی |
| تاریخ به‌صورت سریال اکسل | تبدیل با تصحیح ۱۹۰۰ |
| فایل چند برگ (Sheet) | انتخاب برگ یا ادغام با تأیید |
| سطر جمع/پایان | تشخیص و حذف با علامت‌گذاری |
| ستون خالی انتهایی | حذف |

هر درمان خودکار، در گزارش پیش‌پردازش ثبت می‌شود: «۱۲ سطر عنوان حذف شد، ۴۸۰ ردیف داده شناسایی شد».

### ۴.۲ ویژگی‌های نگاشت

| ویژگی | توضیح |
|---|---|
| تشخیص خودکار | بر اساس نام ستون (فارسی/انگلیسی) + نوع داده + نمونه مقادیر |
| پیشنهاد با اطمینان | هر پیشنهاد، درصد اطمینان دارد؛ < ۷۰٪ برجسته می‌شود |
| تبدیل‌های ستونی | «معکوس علامت»، «ضرب در ۱۰» (تومان→ریال)، «ترکیب دو ستون» (تاریخ+ساعت) |
| ستون ثابت | «همه ردیف‌ها: حساب بانک = 11021» |
| نگاشت شرطی | «اگر شرح شامل کارمزد → حساب 5302» |
| تست نگاشت | دکمه «آزمایش روی ۱۰ ردیف» قبل از اعمال کل |
| ذخیره الگو | برای هر حساب بانکی/نوع فایل، با نام و اثر انگشت |
| نسخه‌بندی | تغییر الگو، نسخه جدید می‌سازد؛ دسته‌های قبلی بازتولید نمی‌شوند |

### ۴.۳ اصلاح در همان صفحه
کاربر می‌تواند **پیش از** ثبت، مقدار یک سلول را در پیش‌نمایش اصلاح کند (مثلاً تاریخ اشتباه). این اصلاح در `sys_data_trace.normalized_payload` با پرچم `manual_edit` ثبت می‌شود.

## ۵. مرحله ۳ — پیش‌نمایش هوشمند و طبقه‌بندی

### ۵.۱ چهار وضعیت ردیف

| وضعیت | رنگ | معنی | رفتار پیش‌فرض |
|---|---|---|---|
| **جدید** | سبز | هیچ مشابهی ندارد | انتخاب‌شده برای ثبت |
| **تکراری** | خاکستری | با سند موجود منطبق است | کنار گذاشته می‌شود |
| **مشکوک** | زرد | نیازمند بازبینی انسانی | نیازمند تأیید صریح |
| **ناقص** | قرمز | داده لازم ندارد (تاریخ/مبلغ/طرف) | قابل ثبت نیست |

### ۵.۲ الگوریتم تشخیص تکراری (BR-521)

```
key_strong = (account_id, business_date, debit, credit, external_ref)
key_medium = (account_id, business_date, debit, credit, normalized_description)
key_weak   = (account_id, business_date, abs(amount), first_12_char(description))

if external_ref موجود:
      تکراری ⟺ key_strong در DB یا در همان فایل
else:
      تکراری ⟺ key_medium در DB
               یا (key_weak در DB و فاصله زمانی < ۲ روز)
```

| قاعده تکمیلی | توضیح |
|---|---|
| تکراری درون‌فایلی | دو ردیف یکسان در یک فایل → دومی «مشکوک» |
| ردیف‌های مشابه با مبلغ متفاوت | «مشکوک» (احتمال ردیف تکراری با اصلاح) |
| تراکنش‌های تکرارشونده واقعی (اقساط) | اگر `external_ref` متفاوت باشد، تکراری نیست |
| دسته‌های قبلی برگشت‌خورده | ردیف‌هایشان «آزاد» می‌شوند و قابل ثبت مجدد هستند |

### ۵.۳ قواعد تشخیص مشکوک

| نشانه | آستانه |
|---|---|
| مبلغ بیش از ۵ برابر میانگین ۹۰ روز همان حساب | زرد |
| تاریخ آینده | قرمز |
| تاریخ قدیمی‌تر از آخرین تطبیق | زرد |
| حساب/طرف حساب شناسایی نشد | زرد |
| مانده بانک پس از تراکنش با گزارش بانک نمی‌خواند | زرد |
| تراکنش در روز تعطیل رسمی با مبلغ بزرگ | زرد |

### ۵.۴ موتور تشخیص تراکنش (Transaction Classifier)

هر ردیف، یک یا چند «پیشنهاد» می‌گیرد:

| قاعده | الگوی شرح | تشخیص | حساب پیشنهادی | اطمینان |
|---|---|---|---|---|
| `IMP-R01` | `ساتنا`, `پایا`, `کارت به کارت` + نام مشتری | واریز از مشتری | `11031` + طرف حساب | بالا |
| `IMP-R02` | `کارمزد`, `حق اشتراک`, `حواله بانکی` | هزینه بانکی | `5302` | بالا |
| `IMP-R03` | `حقوق`, `لیست حقوق` | حقوق | `2104` | بالا |
| `IMP-R04` | `بیمه`, `تأمین اجتماعی` | بیمه | `2105` | بالا |
| `IMP-R05` | `مالیات`, `ارزش افزوده` | مالیات | `21061`/`11071` | بالا |
| `IMP-R06` | `چک` + شماره | وصول چک | `11041` | متوسط |
| `IMP-R07` | `سود`, `بهره` | هزینه مالی | `5303` | متوسط |
| `IMP-R08` | `برق`, `آب`, `گاز` | انرژی | `5203`/`5204` | بالا |
| `IMP-R09` | `اجاره` | اجاره | `5208` | متوسط |
| `IMP-R10` | نام باغدار ثبت‌شده | پرداخت به باغدار | `2101` + طرف | بالا |
| `IMP-R11` | `واریز نقدی`, `شعبه` | واریز نقدی | `1106` شناور | متوسط |
| `IMP-R12` | نام ناشناس + مبلغ بزرگ | نامشخص | `1106` شناور + بازبینی | پایین |

**یادگیری:** هر تصمیم کاربر در این مرحله ثبت می‌شود؛ `imp_rule_suggestion` از تاریخچه یاد می‌گیرد (اگر کاربر ۳ بار یک الگو را به یک حساب نگاشت کرد، پیشنهاد خودکار با اطمینان بالا).

**آستانه تصمیم:**

| اطمینان | رفتار |
|---|---|
| ≥ ۰٫۹۰ | پیشنهاد پیش‌فرض انتخاب‌شده |
| ۰٫۷۵–۰٫۹۰ | انتخاب‌شده ولی با نمایش زرد |
| < ۰٫۷۵ | انتخاب‌نشده، نیازمند تصمیم |

## ۶. مرحله ۴–۵ — ثبت و برگشت

### ۶.۱ ثبت دسته‌ای

| قاعده | جزئیات |
|---|---|
| اتمیک | یا همه ردیف‌های تأییدشده ثبت می‌شوند یا هیچ (BR-525) |
| سند تجمیعی یا تفکیکی | تنظیم: یک سند به‌ازای هر ردیف (پیش‌فرض) یا یک سند تجمیعی ماهانه |
| شماره‌گذاری | سندها شماره پیوسته می‌گیرند؛ ترتیب بر اساس تاریخ و ردیف فایل |
| حجم | تا ۵٬۰۰۰ ردیف در یک دسته بدون افت کارایی |
| پیشرفت | نوار پیشرفت زنده + لاگ |
| خطا | ردیف خطادار، دسته را رد نمی‌کند اگر «ردیف‌های معیوب جدا شوند» انتخاب شده باشد؛ در حالت اتمیک، کل دسته برمی‌گردد |

### ۶.۲ برگشت دسته

```
POST /api/v1/import/batches/{id}/rollback
{ "reason": "فایل اشتباه بانک دیگر — شماره پیگیری متفاوت" }
```

- همه اسناد دسته، سند برگشتی می‌گیرند (نه حذف).
- ردیف‌ها «آزاد» می‌شوند و می‌توان همان فایل را درست وارد کرد.
- سند برگشتی، ارجاع به سند اصلی دارد و در دفتر می‌ماند.

## ۷. تطبیق بانکی (Reconciliation)

```
مانده دفتری بانک  (از دفتر کل)
+ واریزهای در راه (ثبت‌نشده)
− چک‌های صادرشده پاس‌نشده
= مانده بانک طبق صورت‌حساب
```

| حالت | اقدام |
|---|---|
| تراکنش بانک با سند موجود منطبق | «تطبیق‌شده» ✅ |
| تراکنش بانک بدون سند | «نیازمند ثبت» → از پیش‌نمایش ثبت شود |
| سند بدون تراکنش بانک | «در راه» (چک پاس‌نشده، واریز در راه) |
| اختلاف پایدار | مانده «مغایرت» و مسدودسازی بستن دوره |

گزارش `RPT-BNK-004` اقلام در جریان را با عمر (Aging) نشان می‌دهد؛ اقلام > ۹۰ روز نیازمند بررسی است.

## ۸. داده و API

### ۸.۱ جدول‌ها

| جدول | نقش |
|---|---|
| `imp_batch` | دسته: فایل، بانک، کاربر، آمار، وضعیت |
| `imp_batch_line` | ردیف: داده خام، نرمال‌شده، وضعیت، تشخیص، سند تولیدشده |
| `imp_template` | الگوی نگاشت (+ اثر انگشت) |
| `imp_template_version` | نسخه الگو |
| `imp_rule` | قواعد تشخیص/نگاشت شرطی |
| `imp_rule_suggestion` | تاریخچه پیشنهادها و یادگیری |
| `imp_file` | فایل اصلی (پیوست) با هش SHA-256 |

```sql
CREATE TABLE imp_batch (
  id uuid PRIMARY KEY,
  code varchar(32) NOT NULL UNIQUE,
  source_type smallint NOT NULL,        -- BANK_STATEMENT, CUSTOMERS, ITEMS, OPENING...
  bank_id uuid REFERENCES core_bank(id),
  account_id uuid REFERENCES fin_account(id),
  template_id uuid REFERENCES imp_template(id),
  file_id uuid NOT NULL REFERENCES doc_attachment(id),
  row_count int NOT NULL,
  new_count int NOT NULL,
  duplicate_count int NOT NULL,
  suspicious_count int NOT NULL,
  invalid_count int NOT NULL,
  status smallint NOT NULL,             -- UPLOADED..POSTED/ROLLED_BACK
  created_by uuid NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  posted_at timestamptz
);

CREATE TABLE imp_batch_line (
  id uuid PRIMARY KEY,
  batch_id uuid NOT NULL REFERENCES imp_batch(id),
  row_no int NOT NULL,
  raw_json jsonb NOT NULL,
  normalized_json jsonb NOT NULL,
  status smallint NOT NULL,             -- NEW, DUPLICATE, SUSPICIOUS, INVALID
  classification varchar(40),
  confidence numeric(5,4),
  account_id uuid REFERENCES fin_account(id),
  party_id uuid REFERENCES core_party(id),
  amount_debit numeric(20,4) DEFAULT 0,
  amount_credit numeric(20,4) DEFAULT 0,
  business_date date,
  external_ref varchar(80),
  dedupe_key varchar(120),
  voucher_id uuid REFERENCES fin_voucher(id),
  review_note text,
  UNIQUE (batch_id, row_no)
);
CREATE UNIQUE INDEX uq_imp_dedupe ON imp_batch_line(dedupe_key)
  WHERE dedupe_key IS NOT NULL AND status = 0;
```
