## ۳. لایه‌های نرم‌افزاری (Backend)

```
backend/
├─ MazanDasht.Domain/            موجودیت‌ها، Value Object، قواعد دامنه، Event
├─ MazanDasht.Application/       Use Case، Command/Query، اعتبارسنجی، Posting
├─ MazanDasht.Infrastructure/    EF Core، Dapper، فایل، چاپ، دستگاه، همگام‌سازی
├─ MazanDasht.Api/               Endpoint، Middleware، Auth، OpenAPI
├─ MazanDasht.Jobs/              کارهای زمان‌بندی‌شده (استهلاک، Aging، Sync)
└─ tests/
   ├─ Domain.Tests/              فرمول‌ها، قواعد
   ├─ Application.Tests/         Use Case + Posting
   └─ Integration.Tests/         سناریوی سرتاسری روی DB واقعی
```

### ۳.۱ قاعده وابستگی
`Api → Application → Domain`؛ `Infrastructure` فقط از طریق Interface شناخته‌شده در Application تزریق می‌شود. **هیچ ماژول، DbContext ماژول دیگر را مستقیم استفاده نمی‌کند**؛ فقط از سرویس عمومی (`IDataCore`) یا رویداد.

### ۳.۲ مرز ماژول
هر ماژول: `Entities/`, `Commands/`, `Queries/`, `Posting/`, `Permissions.cs`, `ModuleRegistration.cs`.
دسترسی بین ماژولی فقط از طریق:
1. سرویس قرارداد (`I<Module>QueryService`)
2. رویداد دامنه (ترجیح برای واکنش‌های غیرهمزمان)
3. کلید خارجی (`*_id`) برای خواندن گزارش

## ۴. جریان یک درخواست نوشتن (Canonical Write Path)

```
UI (Vue)
  └─ POST /api/v1/sales/invoices  (با Idempotency-Key, Correlation-Id)
       └─ Middleware: Auth, Permission, RateLimit, Validation (FluentValidation)
            └─ Command Handler (اتمیک: یک تراکنش DB)
                 ├─ 1. بارگذاری و قفل داده‌های مرتبط (مرجع، موجودی، دوره)
                 ├─ 2. اعتبارسنجی قواعد کسب‌وکار (BR-…)
                 ├─ 3. محاسبه مبالغ/وزن/کسور (Domain Service)
                 ├─ 4. ذخیره سند + خطوط (وضعیت DRAFT یا POSTED)
                 ├─ 5. DataCore.Write() → خروجی: رویداد دامنه
                 ├─ 6. Posting Engine → سند حسابداری متوازن (اگر قاعده دارد)
                 ├─ 7. Stock Engine → حرکات انبار (اگر مؤثر است)
                 ├─ 8. Outbox.Insert(رویداد)
                 └─ 9. Commit
            └─ Background: Outbox Publisher → BI refresh، نوتیفیکیشن، همگام‌سازی
```

**قاعده:** گام‌های ۴ تا ۸ در **یک تراکنش** هستند. اگر Posting شکست بخورد، سند هم ثبت نمی‌شود. این تضمین VIS-01 است.

## ۶. الگوی آفلاین و همگام‌سازی

### ۶.۱ کلاینت‌های آفلاین‌پذیر

| کلاینت | ذخیره محلی | دامنه آفلاین | سیاست تضاد |
|---|---|---|---|
| باسکول (Electron) | SQLite کامل + صف رویداد | قبض، توزین، صف، چاپ | قبض: «هر دو نگه داشته می‌شود»، ادغام با شماره گره |
| انبار (تبلت/دسکتاپ) | SQLite | حواله، شمارش، انتقال | آخرین حرکت برنده نیست؛ هر دو حرکت ثبت می‌شود (Ledger) |
| فروش (لپ‌تاپ سیار) | SQLite | پیش‌فاکتور، فاکتور، صافی | فاکتور: سرور برنده + ثبت تضاد برای بازبینی |
| مدیر (موبایل) | کش خواندنی | مشاهده داشبورد | فقط‌خواندنی |

### ۶.۲ پروتکل همگام‌سازی

```
POST /api/v1/sync/push      { node_id, change_set: [ {entity, op, id, payload, client_seq, idempotency_key} ] }
POST /api/v1/sync/pull      { node_id, since_revision }
GET  /api/v1/sync/state
```

- **Change-set اتمیک:** اگر یکی از آیتم‌های یک سند وابسته خطا داد، کل مجموعه رد می‌شود (تا نیمه‌ثبت رخ ندهد).
- **Idempotency:** هر آیتم کلید یکتا دارد؛ تکرار ارسال، نتیجه یکسان می‌دهد.
- **تقدم سرور در شماره‌گذاری:** شماره‌های موقت گره (`CUS-A01-000482`) در سرور به کد نهایی نگاشت می‌شوند (`core_code_map`).
- **فشرده‌سازی و بازه:** Push هر ۵ ثانیه در صورت تغییر، Pull هر ۳۰ ثانیه یا رویداد WebSocket.
- **حجم:** فقط Delta؛ تصاویر/فایل‌ها با صف جدا و Resumable Upload.

### ۶.۳ حالت‌های شبکه

| حالت | شرایط | رفتار |
|---|---|---|
| `ONLINE` | اتصال به سرور | همگام‌سازی فعال، BI زنده |
| `LAN_ONLY` | اینترنت قطع، LAN وصل | کار کامل؛ همگام‌سازی محلی؛ به‌روزرسانی ابری ندارد |
| `OFFLINE` | قطع کامل | کار روی SQLite؛ صف انباشت؛ چاپ محلی فعال |
| `DEGRADED` | سرور پاسخ‌گو نیست ولی پینگ هست | تلاش مجدد با Backoff؛ هشدار به کاربر |

نمایش وضعیت همیشه در نوار بالای برنامه: 🟢 آنلاین · 🟡 محلی · 🔴 آفلاین (با تعداد رکورد در صف).

## ۷. استقرارها (Topologies)

### ۷.۱ استقرار تک‌سایتی (پیش‌فرض مازندشت)

```
[سرور داخلی: Win Server 2019 / Ubuntu 22.04]
  PostgreSQL 16 (پورت 5432، فقط localhost/LAN محدود)
  API (Kestrel + Nginx/IIS، پورت 443)
  File Store (D:\mazandasht\files)
  Backup (NAS یا دیسک دوم + ابری اختیاری)
        ▲
        │ LAN 1Gb
   ┌────┴─────┬──────────┬───────────┐
 [باسکول]  [انبار]   [دفتر فروش]  [سردخانه]
```

### ۷.۲ استقرار چندشعبه‌ای

| گزینه | توضیح | مناسب برای |
|---|---|---|
| سرور مرکزی + شعبه‌های Thin Client | همه از LAN/VPN به مرکز | شعبه‌های نزدیک با اتصال پایدار |
| سرور مرکزی + Node محلی با همگام‌سازی | هر شعبه Node آفلاین‌پذیر | اتصال ناپایدار |
| تک‌سرور با `branch_id` | چند شعبه در یک نصب | مدیریت متمرکز ساده |

### ۷.۳ دسترسی از راه دور
VPN (WireGuard) + احراز دو مرحله‌ای + محدودیت IP + لاگ. **هیچ‌گاه پورت دیتابیس به اینترنت باز نمی‌شود.**

## ۹. سازگاری Windows 7 — تصمیم و محدودیت

**واقعیت فنی:**

| جزء | Win 7 | Win 10/11 |
|---|---|---|
| Electron 22 (آخرین نسخه سازگار) | ✅ | ✅ |
| Electron 23+ | ❌ | ✅ |
| .NET 8 (سرور یا کلاینت) | ❌ | ✅ |
| Chromium 108 (داخل Electron 22) | ✅ | ✅ |
| Vue 3 + Vite build | ✅ (خروجی ES2019) | ✅ |

**تصمیم (ADR-0003):**
1. **سرور هرگز روی Win7 اجرا نمی‌شود** (Server 2016+ یا Ubuntu).
2. Win7 فقط به‌عنوان **کلاینت نمایش/ورود** با Electron 22 و بیلد هدف `ES2019` استفاده می‌شود.
3. روی Win7: بدون SQLite محلی پیشرفته، بدون WebSocket اجباری (Polling)، بدون به‌روزرسانی خودکار.
4. Win7 در نسخه ۱.۰ «پشتیبانی محدود» است؛ برنامه مهاجرت به Win10 تا پایان ۱۴۰۵ اعلام می‌شود.
