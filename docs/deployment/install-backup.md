## ۲. نصب (سرور)

```
1. آماده‌سازی OS (به‌روزرسانی، تنظیم منطقه زمانی Asia/Tehran، NTP)
2. نصب PostgreSQL 16 + تنظیمات (max_connections=100, shared_buffers=4GB, WAL archiving)
3. ایجاد دیتابیس و کاربر اپلیکیشن (حداقل دسترسی، نه superuser)
4. اجرای اسکیمای اولیه: database/schema.sql + seed (حساب‌ها، واحدها، بانک‌ها، نقش‌ها)
5. نصب سرویس API (Windows Service / systemd) پشت Nginx یا IIS
6. تنظیم TLS (گواهی داخلی)، HSTS، محدودیت اندازه فایل آپلود
7. اجرای Job Scheduler (Quartz) به‌عنوان سرویس
8. سلامت: GET /health → همه سبز
9. ایجاد کاربر مدیر اولیه + تغییر اجباری رمز
10. آزمون دود: ثبت قبض باسکول آزمایشی، فاکتور، سند، گزارش
```

### ۲.۱ تنظیمات کلیدی PostgreSQL

| پارامتر | مقدار پیشنهادی |
|---|---|
| `shared_buffers` | ۲۵٪ RAM |
| `work_mem` | ۶۴MB |
| `maintenance_work_mem` | ۱GB |
| `max_connections` | ۱۰۰ |
| `wal_level` | `replica` |
| `archive_mode` | `on` |
| `statement_timeout` | ۶۰s (گزارش‌ها با تنظیم جدا) |
| `timezone` | `Asia/Tehran` برای نمایش؛ ذخیره UTC |
| `default_transaction_isolation` | `read committed` |

## ۴. استراتژی پشتیبان‌گیری

| لایه | روش | تواتر | نگهداشت |
|---|---|---|---|
| ۱. WAL Archiving | پیوسته به دیسک/NAS | پیوسته | ۱۴ روز |
| ۲. Base Backup | `pg_basebackup` فشرده | روزانه ۰۲:۰۰ | ۳۰ روز |
| ۳. Dump منطقی | `pg_dump -Fc` | روزانه ۰۳:۰۰ | ۹۰ روز |
| ۴. فایل‌ها | rsync/S3-compatible | روزانه | ۹۰ روز |
| ۵. آفلاین | کپی هفتگی به دیسک خارج از سایت | هفتگی | ۱۲ هفته |
| ۶. سالانه | آرشیو بسته‌بندی‌شده و رمزنگاری‌شده | سالانه | ۱۰ سال (الزام مالی) |

### ۴.۱ اهداف بازیابی

| شاخص | هدف |
|---|---|
| RPO (حداکثر داده از دست‌رفته) | ≤ ۱۵ دقیقه |
| RTO (حداکثر زمان بازگشت) | ≤ ۲ ساعت |
| آزمون بازیابی | فصلی، با گزارش امضا شده |

### ۴.۲ اسکریپت نمونه

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%Y%m%d-%H%M)
DEST=/backup/mazandasht
PGPASSWORD="$PGPASS" pg_dump -h localhost -U erp -Fc mazandasht > "$DEST/db-$STAMP.dump"
sha256sum "$DEST/db-$STAMP.dump" > "$DEST/db-$STAMP.sha256"
rsync -a --delete /srv/mazandasht/files/ "$DEST/files/"
find "$DEST" -name 'db-*.dump' -mtime +90 -delete
# ارسال گزارش موفقیت به /api/v1/sys/backup-report
```

**قاعده:** پشتیبانِ آزمون‌نشده، پشتیبان نیست. هر ماه یک بازیابی آزمایشی روی محیط تست انجام می‌شود، و گزارش آن در `sys_backup_log` ثبت می‌گردد.

## ۵. ارتقا و مهاجرت

| نوع | مسیر | شرط |
|---|---|---|
| وصله (patch) | جایگزینی فایل + restart | بدون تغییر اسکیما |
| نسخه کوچک | migration + restart | با backup اجباری خودکار |
| نسخه بزرگ | پنجره توقف برنامه‌ریزی‌شده | آزمون روی کپی داده واقعی |
| تغییر ساختار حساب | migration + طرح مهاجرت داده | تأیید حسابرس |

**قاعده:** هر migration باید `up` و `down` داشته باشد و در محیط تست با کپی داده واقعی آزمون شود. پیش از هر ارتقا، بکاپ اجباری و بررسی فضای دیسک.

## ۷. مدیریت رخداد

| رخداد | اقدام اولیه | بازیابی |
|---|---|---|
| دیتابیس بالا نمی‌آید | بررسی لاگ PostgreSQL، فضای دیسک | restore از base backup + WAL |
| خرابی دیسک | توقف سرویس، تعویض دیسک | restore کامل |
| حذف اشتباه داده | توقف ثبت | PITR به لحظه قبل |
| کندی ناگهانی | بررسی کوئری‌های سنگین، lock | kill query، ایندکس |
| نفوذ | قطع دسترسی، ابطال نشست‌ها | بررسی لاگ، بازیابی، گزارش |

**PITR نمونه:**
```bash
pg_ctl stop
cp -a /backup/base/* /var/lib/postgresql/16/main/
cat > recovery.signal
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2026-10-10 09:15:00+03:30'
pg_ctl start
```

## ۸. چک‌لیست انتشار

- [ ] بکاپ کامل و آزمون بازیابی انجام شد.
- [ ] migration روی کپی داده تولید تست شد.
- [ ] تست دود: باسکول → انبار → سود → فروش → سند → گزارش.
- [ ] تراز آزمایشی متوازن است.
- [ ] سلامت `/health` سبز.
- [ ] کاربران از تغییرات مطلع شدند (Help Center).
- [ ] پنجره بازگشت (rollback) مشخص است.

## ۹. پذیرش

- [ ] نصب کامل بدون اینترنت، ≤ ۳۰ دقیقه.
- [ ] بازیابی از بکاپ، ≤ ۲ ساعت با صفر خطای داده.
- [ ] آزمون PITR به یک ساعت مشخص، موفق.
- [ ] هیچ migration بدون `down` وجود ندارد.
- [ ] پایش، قطع بکاپ > ۲۶ ساعت را اعلام می‌کند.
