# تیم متخصصان مجازی، حاکمیت و فرآیند تصمیم

سند مرجع: `MD-GOV-001` · نسخه ۱.۰ · مالک: مدیر محصول · تأییدکننده: مالک محصول

---

## ۱. چرا «تیم مجازی متخصص»

سند ۲۰۰–۳۰۰ صفحه‌ای فقط وقتی ارزش دارد که هر بخش آن از نگاه یک تخصص واقعی نوشته شود. یک نفر نمی‌تواند هم فرمول افت بار را درست تعریف کند، هم قاعده تفکیک وظایف را، هم حرکت کاربر در صفحه باسکول را. بنابراین تدوین سند به ۹ نقش سپرده می‌شود؛ هر نقش **مالک** بخشی از سند است و **وتوی تخصصی** دارد.

**قاعده وتو:** اگر مالک یک تخصص بگوید «این طراحی در عمل شکست می‌خورد»، آن بخش تا حل نشود «تأییدشده» علامت نمی‌گیرد — حتی اگر مدیر پروژه موافق باشد.

## ۲. هیئت معماری: نقش‌ها، مالکیت سند و وتو

| # | نقش | مالک کدام اسناد | حق وتو در | شاخص موفقیت نقش |
|---|---|---|---|---|
| ۱ | مدیر محصول (PD) | vision، requirements، ux/quick-create، roadmap | دامنه نسخه، اولویت | کاربر واقعی بدون آموزش، کار روزانه را انجام دهد |
| ۲ | معمار ERP (EA) | architecture/*، data-core، workflow-events، data/ | مدل داده، مرز ماژول، الگوی رویداد | هیچ ماژولی داده دیگری را مستقیم تغییر ندهد |
| ۳ | حسابرس مالی ارشد (FA) | accounting/*، posting-scenarios، reports مالی | ساختار حساب، قواعد سند، قفل دوره | تراز همیشه صفر؛ هیچ سند بدون پشتوانه |
| ۴ | متخصص صنعت مرکبات (CI) | glossary، weighbridge، purchasing، sales، production-packaging | فرمول وزن/افت/سبد/صافی، فرآیند باسکول | اپراتور بگوید «همان چیزی است که می‌خواستم» |
| ۵ | متخصص علم داده (DS) | bi-dashboard، KPI، reports تحلیلی | تعریف شاخص، دانه‌بندی داده | هیچ KPI بدون تعریف فرمول و منبع |
| ۶ | مهندس UX (UX) | ux/*، همه «طراحی صفحه»ها | جریان تعامل، تعداد کلیک، دسترس‌پذیری | زمان ورود هر فرم اندازه‌گیری و کاهش یابد |
| ۷ | گرافیست ارشد محصول (GD) | ui-ux/، print/، هویت بصری | سیستم طراحی، خوانایی چاپ | یک زبان بصری در همه ماژول‌ها |
| ۸ | مهندس شبکه (NE) | deployment/networking-offline، install-backup | آفلاین، LAN، امنیت انتقال | قطع اینترنت، عملیات را متوقف نکند |
| ۹ | روانشناس شناختی (CP) | قواعد ضدخطا در ux، الگوهای ورود داده | بار شناختی، تأییدهای مخرب | نرخ خطای اپراتور < ۰٫۵٪ |

### ۲.۱ قاعده «دو کلید» برای تصمیم‌های حساس

| تصمیم | کلید اول | کلید دوم |
|---|---|---|
| تغییر ساختار حساب‌ها | حسابرس مالی | معمار ERP |
| تغییر فرمول وزن/افت/صافی | متخصص صنعت | حسابرس مالی (اثر مالی) |
| افزودن ماژول جدید | مدیر محصول | معمار ERP |
| تغییر مدل همگام‌سازی/آفلاین | مهندس شبکه | معمار ERP |
| تغییر در قالب چاپ رسمی | گرافیست | حسابرس مالی (الزام قانونی) |
| انتشار نسخه | مدیر محصول | مالک محصول |

## ۳. فرآیند تدوین و تأیید سند

```
پیش‌نویس (Draft)
   │  نویسنده: مالک نقش
   ▼
بازبینی همتایان (Peer Review)         ← ۴۸ ساعت
   │  حداقل ۲ نقش مرتبط
   ▼
آزمون سناریو (Scenario Walkthrough)   ← با داده واقعی یک روز مازندشت
   │  متخصص صنعت + UX + حسابرس
   ▼
تأیید (Approved)  ← امضای مالک + کلید دوم
   │
   ▼
منجمد (Frozen)  ← مبنای کدنویسی؛ تغییر فقط با ADR
```

### ۳.۱ وضعیت‌های سند

| وضعیت | معنا | اثر بر کد |
|---|---|---|
| `Draft` | در حال نوشتن | کدنویسی ممنوع |
| `Review` | در بازبینی | فقط اسپایک/نمونه |
| `Approved` | تأییدشده | کدنویسی مجاز |
| `Frozen` | منجمد برای نسخه | تغییر فقط با ADR + نسخه‌بندی |
| `Deprecated` | بازنشسته | حذف تدریجی |

## ۴. قالب اجباری هر سند ماژول

هر سند ماژول باید دقیقاً این ۱۲ بخش را داشته باشد (ترتیب ثابت). این قالب، خروجی «قابل کدنویسی» تولید می‌کند.

| # | بخش | خروجی مورد انتظار | مصرف‌کننده |
|---|---|---|---|
| ۱ | هدف و دامنه | چه مسئله‌ای، چه چیزی خارج از دامنه | PD |
| ۲ | بازیگران و نقش‌ها | نقش‌ها + مجوزها | امنیت |
| ۳ | فرآیند کسب‌وکار | جریان گام‌به‌گام + استثناها | EA |
| ۴ | موجودیت‌های داده | جدول فیلدها + کلیدها + قواعد | DBA/Backend |
| ۵ | وضعیت‌ها و چرخه عمر | State Machine | Backend |
| ۶ | فرم‌ها و طراحی صفحه | فیلدها، چیدمان، رفتار، کیبورد | Frontend/UX |
| ۷ | اعتبارسنجی و قواعد | BR ارجاع‌شده | Backend |
| ۸ | اسناد حسابداری خودکار | JE ارجاع‌شده + حساب‌ها | FA/Backend |
| ۹ | گزارش‌ها و چاپ | RPT + قالب | DS/GD |
| ۱۰ | مجوزها | ماتریس PRM | امنیت |
| ۱۱ | API | Endpointها + نمونه پیام | Backend |
| ۱۲ | پذیرش و آزمون | سناریوهای UAT | QA |

> اگر بخشی در سند نباشد، در کد هم نباید باشد. «بعداً اضافه می‌کنیم» = بدهی طراحی.

## ۵. ثبت تصمیم‌های معماری (ADR)

هر تصمیم که بعداً «چرا این‌طور شد؟» را ایجاد می‌کند، ADR می‌گیرد.

**قالب ADR:**

```markdown
# ADR-0007 — عنوان تصمیم
- تاریخ: 1404/08/05
- وضعیت: Proposed | Accepted | Superseded | Rejected
- تصمیم‌گیرندگان: [نقش‌ها]
- مرتبط: REQ-..., BR-...

## زمینه
چه مسئله‌ای؟ چه محدودیت‌هایی (فنی، قانونی، سازمانی)؟

## گزینه‌ها
1. گزینه A — مزایا / معایب / هزینه
2. گزینه B — ...
3. گزینه C — ...

## تصمیم
کدام گزینه و چرا.

## پیامدها
- مثبت:
- منفی (بدهی فنی پذیرفته‌شده):
- نیازمند بازبینی در:
```

ADRهای آغازین: `adr/0001-modular-monolith.md`, `0002-postgres-and-sqlite.md`, `0003-windows-7-strategy.md`, `0004-offline-first-sync.md`, `0005-double-entry-enforcement.md`, `0006-jalali-calendar.md`.

## ۷. «تعریف آماده» و «تعریف تمام‌شده»

### Definition of Ready (برای شروع ساخت یک ماژول)
- [ ] سند ماژول `Approved` است.
- [ ] همه موجودیت‌ها با DDL پیش‌نویس و کلیدها مشخص‌اند.
- [ ] همه رویدادها و JEها شناسه دارند.
- [ ] طراحی صفحه (Wireframe) با UX تأیید شده.
- [ ] سناریوی UAT با داده واقعی نوشته شده.
- [ ] مجوزها در ماتریس نقش ثبت شده.

### Definition of Done
- [ ] تست واحد فرمول‌ها و JEها (پوشش ≥ ۹۰٪ در موتور مالی).
- [ ] تست یکپارچه سناریوی سرتاسری (باسکول → انبار → فروش → سند → گزارش).
- [ ] هیچ سند ثبت‌شده‌ای قابل ویرایش نیست (تست منفی).
- [ ] تراز آزمایشی پس از سناریو صفر است.
- [ ] کارایی: فرم اصلی < ۳۰۰ms، گزارش سنگین < ۵ ثانیه.
- [ ] Help Center همان صفحه نوشته شده.
- [ ] لاگ و Audit برای عملیات حساس فعال است.

## ۸. مدیریت تغییر دامنه

| نوع تغییر | مسیر | اثر بر برنامه |
|---|---|---|
| اصلاح متن/برچسب | مستقیم توسط مالک | ندارد |
| افزودن فیلد به موجودیت موجود | ADR سبک + مهاجرت DB | ۱–۳ روز |
| تغییر فرمول مالی/وزنی | ADR + تأیید دو کلید + تست رگرسیون | ۳–۷ روز |
| ماژول جدید | سند کامل + بازبینی هیئت | فاز بعد |
| تغییر ساختار حساب‌ها | ADR + طرح مهاجرت داده تاریخی | ۱–۲ هفته |

**قاعده طلایی:** هر تغییر دامنه که پس از `Frozen` بیاید، باید چیزی از دامنه حذف کند یا تاریخ انتشار را جابه‌جا کند. «همه‌چیز، همین حالا» پذیرفته نیست.
